Prototype, not shipped

Passkey PRF as the recovery route

A live probe that really does create a passkey and derive a secret from it, plus the interaction design that secret would make possible.

1. What this actually is

A passkey normally proves who you are. The PRF extension lets the same passkey also hand back a secret: give the authenticator a fixed salt, and it returns the same 32 bytes every time, on every device where that passkey lives. It never leaves the device unencrypted and the server never sees it.

That secret can wrap Journlet's keeper key, so the keeper key stops living on a device and starts being something any device can unwrap after a Face ID check. No device has to hold it, so no device is the one that must not be lost.

2. How to run this properly

1
On your first device only, press Create. This makes one passkey. Note the result code it produces.
2
On your second device, press Derive. Never Create. Pressing Create again makes a second, unrelated passkey with its own secret, and the two will never match. That is the one mistake that invalidates the test.
3
Paste the first device's result code into the compare box. It will tell you what the answer means, including whether you accidentally compared two different passkeys.
!
If you have already made several test passkeys, delete them all first, or use the device label below so the chooser is readable.

5. The part that surprised me

If the keeper key is unwrappable on any device behind a biometric, then:

  • Any device can show the recovery key. Not just the one that created the journal.
  • Any device can remove another, because rotation needs the keeper key and now any device can get it. The "removal lives on the Mac" consequence goes away.
  • No device stores the keeper key. It is unwrapped for the operation and discarded.

A lost or stolen device is better off than today, not worse: it cannot unwrap anything without passing your biometric, whereas today a keeper device holds the key outright in its keystore.

6. What it costs, stated plainly

  • §6.1 currently says a passkey "must never be presented to the user as protecting journal content". Under this design it genuinely does, so that sentence needs rewriting deliberately rather than quietly bending.
  • Durability of the wrapping secret moves to iCloud Keychain or Google Password Manager. The server still holds ciphertext only, but if you lose that account and the J1 code, you are out.
  • Not every credential manager supports PRF, and a passkey that authenticates but returns no secret looks like a bug rather than an unsupported setup. So the app must probe before offering the route.
  • A device removed from the account keeps the journal it already had. Unchanged from today.

Prototype only. No spec change made, nothing written to the app repo, and per §6.1b this is exactly the kind of feature that has been built and withdrawn twice, so the next step is agreeing the design, not writing it.
