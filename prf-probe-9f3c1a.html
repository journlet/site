Passkey PRF as the recovery route

Two things in one page. The top half is a live probe that really does create a passkey and derive a secret from it, so you can answer spec §11 Q11 on your own devices. The bottom half is the interaction design that secret would make possible.

1. What this actually is

A passkey normally proves who you are. The PRF extension lets the same passkey also hand back a secret: give the authenticator a fixed salt, and it returns the same 32 bytes every time, on every device where that passkey lives. It never leaves the device unencrypted and the server never sees it.

That secret can wrap Journlet's keeper key. The consequence is the whole point: the keeper key stops living on a device and starts being something any device can unwrap after a Face ID check. No device has to hold it, so no device is the one that must not be lost.

2. Live probe

This creates a real passkey named "Journlet PRF test". Delete it afterwards in your password manager. It must run on an https origin, so the preview pane in a chat window will refuse it.

Served from a journlet.com host, it claims journlet.com as the relying party ID rather than the page's own hostname. That matters here specifically: the site is www.journlet.com and the app is app.journlet.com, so a credential bound to either subdomain would be useless to the other. Claiming the registrable domain makes one passkey work across both, which is what the real design needs and therefore what the test has to exercise.

4. The part that surprised me

Working the flows through, this also dissolves the other two pressures without being designed to. If the keeper key is unwrappable on any device behind a biometric, then:

  • Any device can show the recovery key. Not just the one that created the journal.
  • Any device can remove another, because rotation needs the keeper key and now any device can get it. The "removal lives on the Mac" consequence goes away.
  • No device stores the keeper key. It is unwrapped for the operation and discarded, which is the transient-use idea from earlier but with a Face ID prompt instead of a typed code.

A lost or stolen device is better off than today, not worse: it cannot unwrap anything without passing your biometric, whereas today a keeper device holds the key outright in its keystore.

5. What it costs, stated plainly

  • §6.1 currently says a passkey "must never be presented to the user as protecting journal content". Under this design it genuinely does protect it, so that sentence needs rewriting deliberately rather than quietly bending.
  • Durability of the wrapping secret moves to iCloud Keychain or Google Password Manager. The server still holds ciphertext only and Apple never sees your journal, but if you lose your Apple account and the J1 code, you are out.
  • A device removed from the account keeps the journal it already had. Unchanged from today, and worth saying every time.
  • It hangs entirely on the fingerprint test above. Nothing here is worth specifying until that passes on a home-screen PWA on iOS.

Prototype only. No spec change made, nothing written to the app repo, and per §6.1b this is exactly the kind of feature that has been built and withdrawn twice, so the next step is agreeing the design, not writing it.
